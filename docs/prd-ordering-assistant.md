# PRD — 點餐助理（Ordering Assistant）

## Problem Statement

使用者進入咖啡廳網站後，面對菜單上眾多商品（咖啡、茶飲、甜點）不知道如何選擇。現有菜單頁只能瀏覽，沒有任何引導機制幫助使用者根據自身喜好快速找到適合的商品。

---

## Solution

在網站右下角新增一個浮動的「點餐助理」按鈕。點擊後開啟聊天視窗，以對話氣泡的形式引導使用者回答 3 個問題（風味偏好 → 類型 → 口感），最後根據答案從 API 商品資料中篩選出 2–3 件推薦商品，直接呈現在對話視窗內，並提供加入購物車的按鈕。

---

## User Stories

1. 身為訪客，我希望能在任何頁面都看到點餐助理入口，這樣我不需要離開當前頁面就能獲得推薦。
2. 身為訪客，我希望點擊助理按鈕後能看到聊天視窗出現，這樣我能清楚知道互動已開始。
3. 身為訪客，我希望第一個問題是「喝的還是吃的？」，這樣我能快速縮小範圍。
4. 身為選擇「喝的」的訪客，我希望接著被問「咖啡還是茶？」，這樣推薦能更精確。
5. 身為選擇「吃的」的訪客，我希望接著被問「巧克力系還是清淡口味？」，這樣不需要回答咖啡相關問題。
6. 身為訪客，我希望每個問題都以可點擊的選項按鈕呈現，而非自由輸入，這樣操作快速且不容易出錯。
7. 身為訪客，我希望我選擇過的答案以氣泡顯示在對話紀錄中，這樣我能回顧自己的選擇。
8. 身為訪客，我希望選擇後選項按鈕變為禁用狀態，這樣不會誤觸重複選擇。
9. 身為訪客，我希望回答完 3 個問題後，助理說一句結語並顯示推薦商品，這樣體驗有完整的收尾感。
10. 身為訪客，我希望推薦結果呈現商品圖片、名稱和價格，這樣能快速判斷是否合意。
11. 身為訪客，我希望推薦卡片上有「加入購物車」按鈕，這樣不需要跳轉頁面就能直接點餐。
12. 身為訪客，我希望點擊「加入購物車」後有成功提示，這樣確認操作生效。
13. 身為訪客，我希望點擊推薦卡片上的商品名稱或圖片能導向商品詳細頁，這樣能進一步了解商品。
14. 身為訪客，我希望視窗內有「重新開始」按鈕，這樣不滿意推薦結果時能再試一次。
15. 身為訪客，我希望關閉聊天視窗後再開啟，對話紀錄仍然保留，這樣不會因為不小心關閉而遺失進度。
16. 身為訪客，我希望點餐助理在手機上也能正常使用且不擋到主要內容，這樣行動裝置體驗不受影響。
17. 身為訪客，我希望當助理正在「思考」（fetch 商品）時看到 loading 狀態，這樣不會以為程式卡住了。
18. 身為訪客，我希望 API 取得失敗時看到友善的錯誤提示，這樣知道發生了什麼事。

## Implementation Decisions

### 1. 兩個 Composable 分離關切點

- **`useChat`**：管理對話流程。負責 Step 定義、Branching Flow、Messages 陣列、Answers 累積、`sendAnswer()`、`reset()`。
- **`useProductRecommender`**：管理非同步資料流。負責呼叫 API、loading/error/data 三態、根據 Answers 過濾 Recommendation。

兩者在 `OrderingAssistant.vue` 中組合使用，互不干涉。

### 2. `useChat` 使用模組層級 State（單例）

`messages`、`currentStep`、`answers` 宣告在 `export function` 外部，整個 app 共用同一份對話狀態。確保浮動視窗關閉再開啟時對話不中斷。詳見 ADR 0001。

### 3. `useProductRecommender` 使用 per-instance State

State 宣告在 function 內部，只在對話完成時呼叫一次，不需要跨元件共享。

### 4. 商品篩選邏輯（兩階段）

1. 以 Answers 的第一層選擇決定 Category（`咖啡` / `茶飲` / `甜點`）
2. 以後續答案對應的關鍵字比對商品 `content` 和 `description` 欄位
3. 從符合條件的商品中隨機取 2–3 件作為 Recommendation

### 5. Branching Flow 以步驟定義物件實作

Step 定義為靜態資料（物件或 Map），每個 Step 包含問題文字、選項清單、以及「選擇某個答案後跳到哪個 Step」的對應關係。避免用多層 if/else 硬編碼流程。

### 6. 購物車整合沿用現有 `useCartStore`

推薦卡片的「加入購物車」直接呼叫 `useCartStore` 的現有 action，不新增任何 store 邏輯。

### 7. Toast 通知沿用現有 inject 機制

加入購物車成功後，沿用 `ClientLayout.vue` provide 的 `toast.showCartMsg()`，不新增通知系統。

### 8. 元件結構

```
orderingAssistant/
├─ OrderingAssistant.vue   容器：浮動按鈕 + 視窗開關 + 組合兩個 composable
├─ ChatBubble.vue          無狀態展示元件：message type 決定樣式與對齊
├─ OptionButtons.vue       無狀態展示元件：emit 選擇結果給父層
└─ RecommendCard.vue       展示元件：商品資料 prop + emit 加入購物車
```

## Testing Decisions

### 什麼是好的測試

測試**外部行為**，不測實作細節。測試「給定輸入，得到什麼輸出/狀態變化」，不測內部函式呼叫順序或私有變數。

### 測試接縫（Seams）

目前專案無測試設定。建議從最高價值的兩個純邏輯接縫開始：

**接縫 1 — `useChat` 步驟轉換邏輯**
- 給定初始狀態，呼叫 `sendAnswer('喝的')` 後，`currentStep` 應轉到對應下一步
- 給定「喝的 → 咖啡 → 濃郁」的答案序列，`answers` 應累積正確的鍵值對
- 呼叫 `reset()` 後，`messages`、`answers`、`currentStep` 應回到初始值
- 這個接縫不需要 DOM 或 Vue，可用純 TypeScript 測試

**接縫 2 — `useProductRecommender` 篩選邏輯**
- 給定一組模擬商品和 Answers，`recommend()` 應只回傳符合 Category 的商品
- 在符合 Category 的商品中，應優先回傳 description 含關鍵字的商品
- 結果數量應介於 2–3 件
- 這個接縫可 mock 掉 API fetch，只測篩選邏輯本身

**接縫 3（進階）— `OrderingAssistant.vue` 元件互動**
- 點擊浮動按鈕後聊天視窗應出現
- 完成三個問題後應顯示推薦結果區塊
- 點擊「重新開始」後對話應重置

---

## Out of Scope

- **localStorage 持久化**：重新整理頁面後對話重置（視為正常行為）
- **真實 AI 對話**：不串接任何 LLM API，推薦邏輯完全在前端處理
- **溫度選項（冷/熱）**：API 商品資料無溫度欄位，不列入篩選條件
- **後台管理**：點餐助理的步驟與推薦邏輯無需在後台設定
- **使用者登入狀態整合**：推薦邏輯不依賴登入狀態

---

## Further Notes

- 商品分類目前固定為 `咖啡`、`茶飲`、`甜點` 三種，若後台新增分類需手動更新步驟定義
- 推薦結果採隨機取樣，每次結果可能不同，符合「帶點驚喜感」的設計意圖
- 此功能是學習 Vue 3 Composable 的核心練習，重點包含：module-level state 單例、async 三態管理、composable 組合使用
